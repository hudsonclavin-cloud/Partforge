Engine Design Study

How might a computational-engineering system for a rocket engine be organised so that its output means something? This page sketches one answer. It does not design anything.

Educational concept only. Not for fabrication, testing, or flight.

No engine dimensions, propellant recipes, injector specifications, operating setpoints, or build instructions appear on this page. PartForge contains no propulsion, combustion, thermal or structural solver that could produce them. Every data value shown here is synthetic and dimensionless. This page changes nothing in PartForge's generation prompt, flight doctrine, reference data, templates, checks or exports.

Why this page exists

LEAP 71 describes its Noyron system as a large computational engineering model. It encodes physics, engineering logic, production constraints and feedback from tests as software that generates engine geometry from a specification. The company has reported hot-fire tests of engines it generated this way. company claims, as reported; not evaluated here

Look at what carries the weight in that description: encoded physics and test feedback. The geometry is the output. The evidence that it works came from hardware on a test stand. A language model that writes plausible engine code has neither. The same goes for a mesh that looks like an engine, or a geometry check that passes.

None of this is new. NASA's 1989 "rocket engine design expert system" combined three things: a JANNAF standard reference performance code, a finite-element model of how injection, combustion and cooling interact, and rule-of-thumb injector heuristics. The "expert" part was the heuristics. The numbers came from the codes. So the useful question for PartForge is how to keep a system like that honest about what each part of it knows, not how to make an LLM design an engine.

What PartForge checks today, and what it does not

PartForge's flight grade is for passive rocket-club parts: couplers, bulkheads, centering rings, retainers, fins, nose cones and sleds. Its checks work on declared part geometry, measurements of the mesh, reference data and documents. They are not validated propulsion, combustion, thermal or structural solvers, and nothing on this page changes that.

Checks it runs (for parts)

  • The finished mesh is measured against the part's own FLIGHT declaration: bores, hole patterns, outside diameters, extents, revolved profiles and go/no-go gauges.
  • Closed-form engineering checks are recomputed from declared inputs: Lamé thick-wall stress, fin flutter, thread engagement, bolt shear. Room-temperature, typical material values.
  • Mass, centre of gravity and inertia are computed from the mesh at the material's density.
  • Reference-data lookups (airframes, motors, fits, O-rings, fasteners), each with its source and a confidence label.
  • Every tolerance and load input is tagged cited, user or tool default. A check computed from tool defaults reports COMPUTED, not PASS.
  • A part with a hot-gas path or a pressure boundary is classed tier B and gets an interface drawing with a blank inspection column and a list of missing evidence ("hot fire for a nozzle"). Energetic hardware is tier C: geometry is never a sign-off.

Things it does not model at all

  • Thermochemistry or theoretical performance
  • Internal flow, nozzle flow or losses
  • Heat transfer, wall temperature or cooling
  • Combustion stability, injection or mixing
  • Finite-element stress, thermal stress, fatigue or creep
  • Material properties at temperature, or for a specific additive process
  • Transients: start-up, shutdown, throttling
  • Inspection of the as-built article, and tests of any kind

The project's own roadmap evaluated browser FEA, CFD, modal analysis and thermal stress, and declined all four. Each could print a confident number that is wrong in the dangerous direction (docs/roadmap-evaluation.md, "Do not build").

The proposed workflow

Six stages. The loop closes through test results, not through the language model.

1

Requirements & assumptions

Produces
Targets with units, a source and a tolerance for each; written assumptions; an explicit out-of-scope list.
If skipped
The optimizer works hard on the wrong problem, and nobody can tell.
PartForge today
For parts: the SPEC and FLIGHT declarations.
2

Domain models & validity limits

Produces
A registry of versioned models. Each states its assumptions and its validity envelope: the input range it was built and checked for.
If skipped
A number from outside an envelope looks exactly like a number from inside it.
PartForge today
Closed-form part checks only. No propulsion models.
3

Concept & geometry representation

Produces
Geometry generated by code from the model outputs (parametric or implicit), with a digest for every version.
If skipped
A hand edit breaks the chain from requirement to shape.
PartForge today
For parts: the OpenSCAD source is the record of the geometry.
4

Simulation & constraint checks

Produces
Coupled runs, sweeps and optimization. The constraints include "every model input stays inside that model's envelope".
If skipped
The optimizer finds the models' errors and reports them as performance (see the chart).
PartForge today
For parts: the geometry gate and the mesh CMM, against the part's own declaration.
5

Evidence, provenance, uncertainty, status

Produces
A ledger row per claim: source, version, assumptions, uncertainty, evidence class, verification status, what remains unverified.
If skipped
A reviewer can no longer tell measured from computed from guessed.
PartForge today
For parts: cited / user / tool-default provenance, COMPUTED versus PASS, and tiers.
6

Human engineering review

Produces
A decision: accept, reject, or order the test that would decide. Test results recalibrate the models, which gives new model versions and new ledger rows.
If skipped
Nobody is responsible for the result.
PartForge today
A person reads the sheet or drawing. No release status is issued for tier B or C parts.

Read the map as text
  1. Requirements and assumptions go to the orchestrator, which runs the domain models: thermochemistry, flow and performance, heat transfer and cooling, structures, and manufacturing rules.
  2. Model outputs drive the geometry generator. Geometry and model outputs go to the constraint checks.
  3. Model outputs (with their versions) and check results become computed rows in the evidence ledger.
  4. Validation evidence from tests and inspection becomes measured rows in the ledger. It also recalibrates the models, which produces new model versions.
  5. The LLM assistant drafts requirements (a person accepts them), configures runs, and reads the ledger to summarize it. It has no path that writes a verification status.
  6. Human engineering review reads the ledger. It sends requirements back for revision or rejection, and orders tests.

The status scale, strongest first
  • validated by test: a measurement of real hardware, under the conditions claimed. No row on this page reaches it, because nothing here has been tested.
  • verified: the code or the digital model was checked against a reference case or its own declaration. That shows the equations were solved right. It does not show they were the right equations.
  • computed from unverified inputs: the arithmetic is right; the inputs have nobody standing behind them. PartForge reports this as COMPUTED, not PASS.
  • cited, not verified for this use: a published value used outside the conditions it was published for.
  • declared: someone stated it. Nobody has checked it yet.
  • outside validity envelope: a model was asked a question it was never built to answer. The number exists, but it is not usable.
  • not assessed: no model, source or test addresses it.
  • not evidence: a summary, a proposal or a plausible-looking output. It can point to evidence, but it cannot become evidence.
  • illustrative: synthetic, for teaching. It is no claim about any hardware.

What would have to exist before engine-specific analysis is credible

This list is for a student learning computational engineering. None of it is implemented here, and each item is a field of study in its own right.

  1. Verified domain models. Each implementation is checked against published reference cases. That is verification: are the equations solved right? For thermochemistry, NASA's CEA and Cantera are the usual starting points, and their documentation states the assumptions (equilibrium, ideal gas, idealized combustor models) that bound every answer.
  2. Validation data for the regime of interest. The model is compared with measurements. That is validation: are they the right equations? A verified model that was never validated is a precise answer to a possibly different question.
  3. Validity envelopes enforced as constraints. Each model declares the input range it was built and checked for. The optimizer may not leave it, and the ledger flags any result that did.
  4. Uncertainty quantification. This means input uncertainty and model-form uncertainty, propagated through the coupled models. A single number without a spread is a ledger row with an empty field.
  5. Coupling with consistent interfaces. Units, reference conditions and versions must agree between models. Frameworks such as NASA's OpenMDAO exist for multidisciplinary analysis and optimization, but they connect models. They do not make any of them right.
  6. Material data for the actual process and temperature. A typical room-temperature datasheet value says little about a part printed on one machine from one powder lot and run hot. Coupons from that process do.
  7. Manufacturing and inspection capability. Internal passages cannot be checked by measuring a mesh. They need inspection of the built part, such as computed tomography.
  8. Configuration management. Every model, input, geometry and result carries a version or digest, so any ledger row can be reproduced.
  9. A test programme run by qualified people at a suitable facility, with its own safety and regulatory oversight. This lies entirely outside software and entirely outside this page.
  10. Reviewers with the expertise and the authority to reject.

For how the subsystems of a liquid engine relate to one another, NASA SP-125 is a classic textbook. Read it for the system picture, not as a design recipe.

What this page does not establish

  • It does not establish that PartForge can design, analyze, qualify or produce an engine or any engine component. It cannot.
  • Nothing here describes a real engine: no concept, ledger row, number or chart. The chart's values are synthetic and dimensionless, and the ledger rows carry no values at all.
  • None of the following counts as engineering validation: an LLM response, a plausible-looking mesh, a passing geometry check. That includes PartForge's own gate.
  • CEA, Cantera and OpenMDAO are not integrated here. They are named as examples of classes of model.
  • Following a workflow like this one does not make hardware safe. Qualified people, proper facilities and test evidence do.
  • This page has not evaluated LEAP 71's system. It goes no further than what the company has published.
  • It has no effect on flight-part readiness. PartForge's parts are checked exactly as before.

References, and what each is used for

  • LEAP 71, Noyron RP: the inspiration for the architecture. This page describes it only in the company's own general terms, as reported.
  • NASA Glenn, Chemical Equilibrium with Applications (CEA): equilibrium compositions, thermodynamic properties and theoretical rocket performance. These are an example of one domain model and its assumptions.
  • NASA NESC, TB-26-04, Updates and modernization of CEA. CEA v3 is a modern Fortran rewrite with C, Python, MATLAB and Excel interfaces. The bulletin advises keeping engineering review and validation when established workflows move to it. That advice is the pattern this page follows: even a trusted solver's new version is a new ledger entry.
  • Huzel & Huang, NASA SP-125, Design of Liquid Propellant Rocket Engines (second edition): how thrust chambers, turbopumps and valves relate to the whole engine. Used here for the system picture only.
  • K. J. Davidian, A rocket engine design expert system (NASA Lewis, JANNAF Combustion Meeting, 1989). The precedent: performance code, finite-element model and heuristics, combined.
  • OpenMDAO: NASA's open-source framework for multidisciplinary analysis and optimization. An example of the orchestrator box.
  • Cantera: an open-source toolkit for chemical kinetics, thermodynamics and transport processes. A second example of a thermochemistry model.
  • PartForge: README (flight grade, provenance, tiers), STATUS (what is verified and by what), headless/README (the measured / derived / cited confidence an agent receives).
